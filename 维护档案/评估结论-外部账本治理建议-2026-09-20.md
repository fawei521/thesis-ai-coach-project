# 评估结论：外部"账本治理"建议（2026-09-20）

> **为什么留这一份**：一份外部 AI 建议把本仓的多处记账改成"一份 YAML 主账 + 派生视图 + CI 校验"。
> 逐条实测核对后**不采纳改造**，只采纳它指出的三处可验缺陷。否决决定若不留证据，几个月后一定被重新提出、
> 再论证一遍。本文区分**实测确认**（给命令与 file:line，可复跑）与**判断**（可争议的取舍）。
> 本目录规矩不变：**只进不改**。

## 一、建议原文要点（外部 AI，2026-09-20）

"一主账、七派生、三校验、二入口、一监管"：每次变更只写一份 Change Record（YAML，字段含
type/status/scope/impact/verification/artifacts/rollback/ai/views），七本账改为从主账与 CI/CD 派生，
CI 做主账校验＋派生一致性校验＋可执行校验，AI 只读入口与 manifest 按需加载，人只审主账 diff 与异常。
待办迁到 issue 看板，记忆只留 ADR。

## 三、实测确认：真实缺陷（本版已修）与它的诊断差异

1. **同一事实没指定唯一的家**（≠"账本太多本"）。实测：`README.md` 内 `:102` 写"16种量表"、`:38` 写"24组"，
   而 `psychology/scale-library.md` 的 `### N.` 编号实测到 39（`CHANGELOG.md:45` 记录 v1.63 已 29→39）。
   **两个错数在同一个文件里互相打架**——只留一本账也照样漂。故修法是把数字收归本体、别处只留指针，
   而不是把 16 改成 39（下次扩库还会错）。同理 `README.md:145` "9个模块" vs `AGENTS.md:73` "13 个模块"（实测 13）。
   **判断**：这是本仓唯一由这次评估证实的结构性缺陷，与账本"本数"无关。
2. **发出去的账本引用了查不到的编号**。`CHANGELOG.md:134/156/195/222` 引用"待办 P16/P9/P15/P7"，
   仓库内 grep 无任何定义处；定义在仓库外 `_归档/待办计划-拆分与发版收尾.md`，而 `E:\毕业论文` 本身不是 git 仓库
   （实测 `git rev-parse` → not a repository）→ 不受版本管、断言看不见。已补 `维护档案/待办编号索引.md` + 断言。
   **它建议的"Change Record 主账"在这一点上确实对症**——但完整 YAML 主账要付的代价远大于补一个编号索引。
3. **同一件事写两遍**。`AGENTS.md:41-45` 列四条门禁命令，其中三条本来就在 `full_e2e.py` 内部执行
   （`case_02.py:133`、`case_04.py:138/153`、`case_05.py:123/167`），只有 `py_compile` 漏在外面。已并入并收敛成一条。

**它没测到、但我们自己撞过的**：`size_baseline.txt:4` 注释把 `full_e2e` 列为 LEDGER 豁免，
而同文件 `:6` 与 `size_ratchet.py:41-45` 的代码都说它不豁免——注释过期。这类"规则本身被抄了一遍"的漂，
主账方案同样治不了（AI 照样会在两处各写一句）。

4. **⚠️ 断言会把错数字锁成"正确答案"——这条是修 ① 当场撞上的，也是本次评估最重要的自我修正。**
   改掉 README 的"16种"后回归判红：`case_03.py:106` 原来写着
   `check("README数字修正", "16种" in rm and "10种统计方法" not in rm)`——
   某个历史版本把"10种统计方法"改成当时的正确值"16种"，**并用断言钉死了它**。
   于是：真值 29→39 变了两次，README 里的"16种"因为"有断言保护"反而一直没人敢改，
   **机器校验反过来给漂移续命**。现已翻成反向钉（三个过期值一律不得出现）。
   **判断（写给以后的 AI）**：断言只有在**钉住不变量**时才防漂；钉住"某个时刻的具体值"就是定时炸弹。
   加断言前先问一句：这条以后改了要不要连断言一起改？要——那它就该钉"不抄数字"或"指向本体"，而不是钉数字本身。
   与 `CONSTITUTION.md:88-89`"规则也算功能、要有能复跑的判据"不矛盾：判据本身也要选对层次。

## 四、拒绝项与理由（判断，附实测成本）

- **YAML 主账 + `ledger/manifest.yaml`**：一次变更现已需同步约 8 个文档目标（`DEVELOPMENT.md:77`），
  再加一份 30 字段的机器账＝多一处要同步、且要新写一套生成器与校验器。它自己也警告
  "模板必填字段要真有信息，否则 AI 会写废话填满"。**判断**：对单人项目净收益为负。
- **CI**：本仓零 CI（无 `.github/`、无 git 项目钩子，两个 hook 是 Qoder 自带的、`|| true` 永不阻断）。
  且到 GitHub 链路八次实测 443 不通（记录在仓库外待办文件 P0 一节）。**跑不起来的 CI 比一定跑得起来的本地闸更差**——
  本仓的门禁已经是本地四条命令、772 项断言，把它搬到 Actions 只是换地方，不增加任何保证。
- **待办迁 issue 看板**：远端不可靠是实测事实；且真问题是"P 号不在 git 里"，不是"待办不该是文件"。
  迁走反而丢掉离线可用（本项目整个产品形态就是"离线文件夹交给 AI"）。
- **CD 生成不可变发布记录**：没有 CD。发布是手工 `git archive` + 双产物逐字节比对（`DEVELOPMENT.md:103-109`），
  这条流程至今是唯一抓出真 bug 的环节，不能为了"自动化"拆掉。**它"AI 不得重写历史发布记录"这条原则我们已采纳**
  （`维护档案/README.md:11` 只进不改）。

## 五、重开条件（出现任一，就重新评估主账改造）

1. 有第二个真人贡献者、开始收外部 PR（现在 153 个 commit 全为同一本地身份）。

4. **同类"同一事实两处不一致"一个月内再被实测抓到 ≥2 次**——说明靠单点断言补漏已追不上手写速度，
   那时该考虑把事实集中到一份机器可读的账上。
