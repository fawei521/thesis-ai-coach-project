**v1.106 账本补齐六版，并给"断更"装一把会判红的尺**
> 发布：2026-10-02

- **为什么做这一版**：`tests/e2e-test.md` 是断言的账本，它从 v1.99 起断了六版——索引停在测试97（v1.98），
  下一行直接跳到测试98（v1.105）。中间这些版一共加了 224 条断言（逐版现量：70／60／11／7／13／63），
  没有一行账。`case_15` 早就在看这张索引，但它量的是**行的形状**（编号在不在索引里、不重不漏），
  整版缺席这种坏法它一辈子报不出来。**只把旧账补上它就会再断一次**，所以这一版两件一起做（待办 P41）。
- **旧账补成七行**：测试97a–97f 对应 v1.99…v1.104，测试98b 是 v1.105 没点名的另一摊
  （开局必读总量闸、场景用法单源、菜单清单逐字同源）。正文放在
  `维护档案/e2e-test-断更补记-v1.99至v1.105.md`，索引只留一行——**已发出去的编号不重排、不改号**，
  所以用父号加尾缀。每行写清"哪一版、落在哪个 `case_NN`、加了什么判据、踩过什么坑"。
- **新尺 `tests/e2e_cases/case_34.py`（八条）**：台账自己声明一句"逐版覆盖起点：v1.99"，
  这把尺就把起点之后每一个 tag 的断言名抽出来与上一个 tag 比差集，凡新增过断言的都必须被索引行的**用例列**点名。
  五件必备按顺序钉：起点在位且是真实 tag（**删掉这句判红**，不许静默全绿）→ 抽取器量得到东西 →
  真账过 → 阴性两格（抹掉最新那版的行必须点出它；把所有行的版本号遮成 x，名单必须恰好等于"有新增"的全集，
  证明名单是算出来的不是写死的）→ 阳性一格（把起点推到最新 tag，名单就该空——**红来自差集不来自名单**）。
- **它的软肋写在明面上**：口径是"断言名的字面量差集"，所以**改写一句判据名会被算成新增**（那就得回来补一行），
  而一条判据没加、只搬家的版本不会被要求登记。行里的"+N"是登记当时的读数，**这把尺不对账条数**——
  拿它对账只会养出一见数字不符就红、于是没人敢改判据的尺；"记了几条"留给人判。
  它只在开发树跑：学生副本没有 git 历史与历史 tag，按 `case_30` 的先例整片跳过。
- **顺手订正一处会骗人的注释**：`full_e2e.py` 给 `case_33.py` 写的分册注释是"v1.106"，而它实际随 **v1.104** 发出
  （断言名里那串 `v106 ` 前缀是作者当时的写法，不改——改名会让下一版的差集虚增 17 条）。
  **注释会骗人，差集不会**，这就是这把尺存在的理由。
- **学生侧看到的变化**：只有版本史多这一条，以及 `START.md`／`README.md` 的版本行。
  菜单、工具、随包规则文档一个字没动；`tools/style_check.py`（上一版顶在代码档上限的那件）这次没碰。
  **包件数与体积都不变**——新增的正文与尺子全在 `tests/` 与 `维护档案/`，按设计不随包分发。
- **代价照实记**：`README.md` 被这一版的版本段顶到只剩一条缝（上限与余量都由 P42 登记、数字现量不抄在这里），包内版本史也再次滚出一版——**下一版发版前得先处理 P42**，别指望这次那道闸还给你留着地方。
