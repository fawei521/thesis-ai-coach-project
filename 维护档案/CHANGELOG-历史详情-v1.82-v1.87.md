**v1.86 输出编码守卫改为无条件生效（修一处"假失败"）**
- **现象**：`python tests/consistency_check.py >/dev/null` 退出码 1，输出里却**一条漂移都没有**；
  把 stderr 单独收下来才看到真因——`UnicodeEncodeError: 'gbk' codec can't encode character '↔'`（标题里的"↔"）。
- **根因**：全套件 35 个可运行脚本的守卫都写成 `if hasattr(sys.stdout, "reconfigure") and not sys.stdout.isatty():`。
  Git Bash 的 `/dev/null` 与 Windows 的 `nul` 都是**字符设备**，`isatty()` 返回 True → 守卫以为在真控制台、跳过 UTF-8 归一，
  退回 GBK 后打印特殊字符就崩。表现是"尺子自己报错"，容易把人引向去查一个不存在的漂移。
- **取证再动手**：用 `CREATE_NEW_CONSOLE` 起真控制台子进程实测——`isatty()=True` 且 `sys.stdout.encoding` **本来就是 utf-8**，
  `reconfigure(encoding="utf-8")` 成功且是恒等变换 → **去掉 isatty 判断对学生双击 bat 的场景零影响**，不是拿猜当判据。
- **改法**：35 个文件、35 处守卫条件统一改为 `if hasattr(sys.stdout, "reconfigure"):`（**净零行**，不动任何输出内容）；
  口径写进 `DEVELOPMENT.md` 阶段 B。
- **顺手修一处真实漂移**：`menu.py` 顶部分册注释还写着"两组分放 menu_data/menu_lit"，而 v1.85 已加第三册
  `menu_thesis.py`（我自己上一版漏改）。注释改为按主题点名列出，并**删掉写死的处理器条数**——
  条数由 `MENU` 表与"分母等于项数"那条自己数出来，不再制造下一次漂移。
- **测试**：full_e2e 685→**689 项**（+4：`v186 输出丢给 NUL 时守卫脚本不假报失败`、
  `v186 守卫条件全仓库统一为无条件生效`、`v186菜单注释点名的分册齐全且真实`、`v186菜单注释不再写死处理器条数`）。
